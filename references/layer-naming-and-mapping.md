# 图层命名与分类映射

## 为什么要先看图层

脚本不会"看图说话"。用地性质来自**图元所在图层名**，因此图层命名是整套测算的第一手依据。开工前先列出图纸图层清单（`cad_env_check.py --list-layers` 或 `land_area_report.py --list-layers`），再决定映射配置。

默认按**填充优先**识别：用地色块（HATCH）通常画在独立的用地图层上，多段线常是辅助线或未闭合边线。因此映射规则实际作用于「填充图层名」，多段线只在填充缺失时才使用，同一套规则两类图元通用，无需维护两份配置。

## 映射配置结构

配置文件为标准 JSON（UTF-8），示例见 `assets/mapping.2023.example.json`：

```json
{
  "standard": "2023",
  "ignore_layers": ["0", "Defpoints", "TK*", "图框*"],
  "strip_prefixes": ["YD-", "用地-", "GH-"],
  "rules": [
    {
      "code": "0701",
      "exact": ["居住用地", "R2", "0701"],
      "regex": ["^R[12]$", "^07-?01$"],
      "keywords": ["住宅", "居住"]
    }
  ]
}
```

| 字段 | 作用 |
| --- | --- |
| `ignore_layers` | 不参与统计的图层，支持 `*`、`?` 通配符（`fnmatch` 语法），常用于图框、轴线、标注、图例 |
| `strip_prefixes` | 匹配前先剥掉的命名前缀，让 `YD-居住用地`、`GH-公园绿地` 能命中同一规则 |
| `rules[].exact` | 整名精确匹配，忽略大小写与首尾空格 |
| `rules[].regex` | 对整名做 `re.search`，用于 `R1`、`R2`、`07-01` 这类编号式命名 |
| `rules[].keywords` | 子串包含匹配，作为兜底，如"住宅""公园" |
| `rules[].code` | 目标分类代码，必须存在于当前 `classification.*.json` 中 |

## 匹配优先级

```
忽略图层 → 剥离前缀 → 整名 exact
  → 混合用地拆段：逐段「代码点名 → 分类表中文名 → exact → regex → keywords」
  → 整名代码点名 → 整名分类表中文名 → 整名 regex → 整名 keywords → 未识别（进入待确认清单）
```

**只有中文名时**用分类表原名精确匹配：`二类城镇住宅用地` → 070102、`15分钟社区生活圈综合公共服务设施用地` → 0809。名字与表内不一致（简称、错别字）不猜，走确认项问用户。

**代码点名优先**：图层名里出现分类表中真实存在的完整代码（`090101`、`0807`、`R11`）就直接归到该代码，最长者胜，不降级到上位类（`090101` 不会变成 `0901`/`09`）。两位代码（`01`、`07`）只有整个图层名就是它时才算，避免「标注-01」被当成耕地。

同一规则内多条件命中不重复计面积；同一图元只归入**第一个命中的规则**，规则顺序即优先级，把更具体的规则写在前面（例如"防护绿地"要排在"绿地"之前，"农村道路"要排在"道路"之前）。

## 图层名里的代码没登记（必须问，不许兜底）

`代码点名` 只认分类表里**真实存在**的代码。图层名是「代码 + 名称」但该代码没登记时（如 `090201 研发设计用地`、`0909 商业服务业混合用地`），会继续降级到 regex / keywords，被别的大类抢走：本次事故里 `090201 研发设计用地` 被 0802 的「研发」关键词吞掉 **88.78 ha**，08 类虚高、09 类虚低，`0901` 也被 `0909` 的 9.30 ha 顶到 31.43。

这类名字出现时，脚本必须输出 `unregistered_code` 确认项并中断（退出码 3），**未确认前不生成平衡表**，原样问用户两件事：

1. 图层名是否写错？写错就改图层名后重跑（不带任何参数）。
2. 名称无误时，是否把 `CODE 名称` 登记为新增用地代码？

三种回填：

| 用户答复 | 参数 | 效果 |
| --- | --- | --- |
| 名称无误，新增代码 | `--add-code "0909:商业服务业混合用地:2:09"` | 写入分类配置 + 指引表，按新代码归类 |
| 归入已有类目 | `--unregistered-code "090201=map:0902"` | 不新增类目，显式指定归属，报告说明记录 |
| 本次先不处理 | `--unregistered-code "090201=skip"` | 沿用关键词兜底，报告标需复核，禁止交付 |

关键词兜底只适用于「图层名里根本没有代码可依」的图层（如 `商业用地`、`公服`）；一旦有代码可依，就必须先确认代码归属。

## 旧标准图纸（GB 50137）

图层名是 `R2`、`B1`、`A33`、`M1`、`S1`、`G1`、`U11` 这类代码时，图纸用的是 2011 版标准。处理顺序：

1. **先问用户**：按旧标准统计并换算为 2023，还是直接按 2023 表重映射？
2. 要换算：`--standard gb50137 --convert-to 2023`。换算表为 `assets/conversion.gb50137_to_2023.json`（来源：新老代码对照表）。
3. 换算查不到对应时按上位类回退（`R21` → `R2` → `R`）；歧义代码（`E2`、`Ej`、`H14` 同时对应多个新类）列入待确认，不硬归。
4. 不想换算就 `--standard 2023`，但要在报告里说明「按新表重映射，非标准换算」。

## 混合用地命名

图纸里常见 `0802+0903`、`0802+0903(30%)`、`R2/B1` 这类写法。技能的处理口径：

1. 先整体名匹配（配置里若显式写了 `0802+0903` 规则则优先命中）；
2. 未命中则按 `hybrid_separators`（默认 `+ ＋ / ／ 、 & ，`）拆段，去掉 `(...)` 尾注；
3. **各段代码用 `+` 连成新代码，单独成行**：`070101+0809`、`0807+090101`，名称同样用 `+` 连接；
4. 新行的层级、父级与排序跟随**首段代码**：首段二级 → 同级二级行（`0807+090101` 挂在 08 下），首段三级 → 三级行并紧跟首段之后（`070101` → `070101+0809` → `070102`）；
5. 面积独立计量，再按三级→二级→一级逐级加和；某段既非表内代码也非表内名称时，输出 `hybrid_unresolved` 确认项问用户（名称写错 / 新增代码 / 只按首段统计），不得拼假代码。

报告附表列出 原图层 → 新增代码。示例：`070101:30`、`070102:50`、`070101+0809:50` → `0701:130`、`07:130`。若新行的次类跨一级类（如 08+09），面积仍全额计入首段所属一级类，报告说明节会标注。

## 未识别图层的处理

1. 报告中的"待确认清单"逐条列出图层名、图元数、面积合计 —— 这是**正常输出**，不是错误。
2. 让用户确认每个图层对应的用地性质，把结论补进 `mapping.*.json` 后重跑。
3. 若某图层是辅助线或图例，加入 `ignore_layers` 而不是硬套分类。
4. 不要为了"凑齐 100%"而把未识别面积并入其他类目，这会让平衡表失真。

## 调优建议

- 图层名带编码但编码不统一时，优先用 `regex`；命名混乱时用 `keywords`，但要接受误判风险并在报告中提示置信度较低。
- 每次调整映射后重跑并对比"待确认清单"是否清空，是检验配置质量最快的办法。
- 建议每个项目把最终 mapping 文件随成果一起归档，便于复核与复用。
